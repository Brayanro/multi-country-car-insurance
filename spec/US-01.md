# US-01 — Policyholder and Vehicle Data Form

**Status:** Human approved  
**Version:** Draft 3  
**Source:** `requirements/technical-assessment.pdf`, pages 2–3 (technical requirements), 6 (story, context, business rules, and acceptance criteria)  
**Related story:** US-01 — Policyholder and vehicle data form

## Objective

As a person interested in insuring my car, I want to enter my data and my vehicle's data in a simple form, so that I receive insurance options suited to my country and my vehicle.

The first wizard step displays the published field configuration for the selected country, in its configured order. The user can complete the form and continue only when the configured field validations and the story's age and vehicle-year rules pass. Returning from step 2 retains entered data.

## Scope and boundaries

### In scope

- Render the form fields configured for the current country, including each field's label, type, required status, validations, help text, configured error messages, order, and country.
- Support the source-listed field types: text, number, select, date, and checkbox.
- Obtain select options from Strapi.
- Enforce the vehicle-year and policyholder age rules approved at the human checkpoint.
- Derive country context from the application URL using `co` and `cl` as canonical ISO 3166-1 alpha-2 path segments. When the URL has no country, display a country selection screen. Do not silently default or redirect to another country.
- Keep quote data isolated by country.
- Require every dynamic field to have a unique stable identifier independent of its display label and order.
- Reconcile saved values with published configuration changes according to the human-provided rules below.
- Apply the human-provided validation operators, value formats, and progressive-validation behavior below.
- Display Spanish field labels, help text, and validation errors for both countries.
- Show the configured validation error beside the relevant field and block continuation while invalid.
- Reflect a newly published field after the user reloads, without an Angular code change or redeployment.
- Retain the form data when the user returns from step 2 to step 1.
- Cover Colombia and Chile configurations in acceptance-level verification.

### Out of scope for this story

- Plan listing and plan selection (US-02).
- Summary, terms acceptance, and simulated payment (US-03).
- A real insurance rating service or payment integration.
- Exact identity-document or license-plate validation rules. The assessment names country-specific document and plate examples but does not specify validation formats.
- The Angular route structure, exact configuration schema, and technical validation mechanisms. These are for the architecture stage after approval of this specification.
- Identity document and license plate validation patterns beyond treating both values as strings.

## Functional behavior

### Country-specific configuration

The application URL is the source of truth for the active country. The canonical country path segments are lowercase `co` and `cl`, corresponding to ISO 3166-1 alpha-2 codes. The architecture may accept uppercase equivalents and normalize them to lowercase. If no country segment is present, show a country selection screen. If the segment is unsupported, show a clear error and allow the user to select a supported country. Do not silently default or redirect to another country. The exact Angular route structure is deferred to architecture.

Given the URL identifies Colombia or Chile and published form-field configurations exist for both countries, when the user opens step 1, the app displays only fields for that URL country and orders them by configured order. Quote data remains isolated by country. Country-specific fields, options, validations, and copy come from Strapi.

Country examples to include in test fixtures:

- Colombia: a configured identity-document field supporting the assessment's cédula de ciudadanía or cédula de extranjería examples, and a vehicle registration field labeled for placa.
- Chile: a configured identity-document field supporting the RUT example, and a vehicle registration field labeled for patente.
- In both countries, display configured form labels, help text, and validation errors in Spanish.

These examples do not prescribe particular input masks, validation expressions, labels, or control implementations. Those details must come from the published country configuration or an approved decision.

### Configured field types and validation

Use these field value formats from the human clarification. Identity document numbers and vehicle license plates are strings.

| Field type | Value format |
|---|---|
| Text | String |
| Number | Number |
| Select | Stable option identifier |
| Date | ISO calendar date in `YYYY-MM-DD` format |
| Checkbox | Boolean |

Support the following validation operators. Each configured rule has its own error message, and an individual field displays at most one error at a time. Evaluate all rules, selecting the required-field error first and otherwise the first failing rule in configured order. Validation operators must be compatible with their field types. The operator-to-type compatibility matrix, rule parameter schema, and technical validation mechanisms are architecture details.

| Operator | Required behavior |
|---|---|
| `required` | Validate that the field has a value according to the field type and approved required semantics. |
| `minLength` | Validate a configured minimum length. |
| `maxLength` | Validate a configured maximum length. |
| `pattern` | Validate a configured text pattern. |
| `min` | Validate a configured numeric minimum. |
| `max` | Validate a configured numeric maximum. |
| `minDate` | Validate a configured earliest date. |
| `maxDate` | Validate a configured latest date. |
| `email` | Validate an email value. |
| `minimumAge` | Support the policyholder legal-age requirement of at least 18 on the validation date. |
| `vehicleYearRange` | Accept a vehicle year from current calendar year in the user's locale minus 20 through that year plus 1, inclusive. |

For a required select with one or more valid options, show a non-selectable placeholder and leave the value unset until chosen. Do not auto-select the first option. The empty selection is invalid and its configured required error appears on blur or an attempt to continue. A required select with zero valid options is an invalid configuration and makes the form unavailable, as described under configuration errors below.

Do not show validation errors on initial render. Show an error when a user leaves an invalid field. After a field is touched, update its error whenever its value changes and clear the error immediately when valid. On continue, validate every field, show applicable errors, prevent progression if invalid, and move keyboard focus to the first invalid field. Keep Continue available once configuration is ready. Error messages come from Strapi and must be accessibly associated with their fields.

### Age and vehicle-year rules

- Use the configured date-of-birth value to require that the policyholder is at least 18 years old on the validation date. This is the human-approved interpretation of the assessment's legal-age rule.
- The vehicle year must be within the inclusive range from the current calendar year in the user's locale minus 20 through that calendar year plus 1. The inclusive boundaries are the specification's interpretation of the assessment's wording.

### Configuration updates and retained data

Cache form configuration in memory during the quoting session. Refresh it when the app reloads and when the user switches countries. Never present a stale configuration as current. A temporary configuration failure preserves prior quote data while the recoverable error is shown. When valid configuration becomes available, reconcile values and revalidate the whole form.

Reconcile values by stable field identifier. Discard values for removed fields and for identifiers that changed. Preserve values when fields are reordered or labels/help text change. Initialize new fields empty or from a configured default. Preserve compatible values after validation-rule changes and revalidate them. After a field type change, preserve a value only if it is compatible with the new type, otherwise clear it. Clear a select value when its option is removed. Remove discarded or incompatible values from active persisted state and from any quote summary. Prevent progression whenever the reconciled form is invalid.

The technical implementation of the in-memory cache and reconciliation is an architecture decision. See the remaining architecture questions for default-value and compatibility semantics that the human clarification does not define.

After completing step 1 and moving to step 2, returning to step 1 shows the user's previously entered values. The persistence mechanism is an architecture decision.

## Configuration and validation contract

The assessment explicitly requires the listed field properties below. Human checkpoint feedback additionally requires a stable field identifier and permits a configured default for new fields.

| Property | Requirement and provenance |
|---|---|
| Label | Human-readable label for the field (assessment) |
| Type | One of text, number, select, date, or checkbox (assessment) |
| Required | Whether a value is required (assessment) |
| Validations | Configured validation constraints (assessment, expanded by human clarification) |
| Help text | Configured guidance text (assessment); whether it may be omitted is unspecified |
| Error messages | Configured validation message (assessment); one message per configured rule (human clarification) |
| Order | Position in the country's form (assessment) |
| Country | Country to which the field applies (assessment) |
| Select options | Options supplied by Strapi for select fields (assessment); each submitted value is a stable option identifier (human clarification) |
| Stable field identifier | Unique and stable across label or order changes (human clarification, not stated in the assessment) |
| Default value | A new field may initialize with a configured default (human clarification); representation and validation are deferred to architecture |

The front end must treat incoming configuration as runtime data and validate it before using it to render or validate fields, consistent with the project requirement for typed configuration models and explicit runtime validation. The schema versioning, option shape, technical representation of the required stable identifier, field data key, supported validation operators and types, and behavior for malformed or unsupported configuration remain for the architect to propose and the human to approve.

## Acceptance criteria

The test IDs below provide stable traceability from the story to later tests. Proposed test locations and framework are intentionally left to implementation planning.

### AC-US01-01 — Country configuration and order

**Given** published form fields are configured for Colombia and Chile and the application URL identifies Colombia using canonical `co`  
**When** the user opens step 1  
**Then** only Colombian fields are displayed in configured order  
**And when** the application URL identifies Chile using canonical `cl` and the user opens step 1  
**Then** only Chilean fields are displayed in configured order  
**And** country-specific content comes from Strapi.

### AC-US01-02 — Configured validation blocks progression

**Given** the form has valid configuration and the user has not interacted with a field  
**Then** no validation error is shown for that field  
**When** the user leaves an invalid field  
**Then** that field's applicable rules are evaluated and its configured error is accessibly associated with it  
**When** the user changes a touched field  
**Then** its errors update and clear immediately when it becomes valid  
**When** the user attempts to continue  
**Then** all rules for all fields are evaluated  
**And** no more than one configured error is shown per invalid field  
**And** a required-field error takes precedence, followed by the first failing configured rule  
**And** an invalid attempt to continue is blocked and moves keyboard focus to the first invalid field  
**And** Continue remains available once configuration is ready, even when the form is invalid  
**And** a valid form can continue.

### AC-US01-03 — Vehicle year boundaries

**Given** the current calendar year in the user's locale is Y  
**When** the user enters a vehicle year  
**Then** years Y−20 and Y+1 pass the vehicle-year range validation  
**And** years earlier than Y−20 or later than Y+1 fail that validation  
**And** the configured vehicle-year validation error is displayed according to AC-US01-02.

### AC-US01-04 — Policyholder age

**Given** the form contains the policyholder's date of birth  
**When** the user's age on the validation date is less than 18  
**Then** validation fails with the applicable configured error message and progression is blocked  
**And** a user who has reached age 18 on the validation date passes this rule.
### AC-US01-05 — Published field change appears after reload

**Given** a field configuration has changed in Strapi for a country  
**When** the user reloads the application or switches the URL to that country  
**Then** the refreshed configuration includes the published change without a frontend code change or redeployment.

### AC-US01-06 — Data retained on return

**Given** the user completed step 1 and moved to step 2  
**When** the user returns to step 1  
**Then** previously entered data is still filled in.

### AC-US01-07 — Field types and configured properties

**Given** the country configuration contains text, number, select, date, and checkbox fields, with unique stable identifiers, Spanish labels and help text, required flags, validations, and Spanish error messages  
**When** step 1 renders  
**Then** each field shows its configured label and help text  
**And** required-field validation follows the configured required flags  
**And** each supported type accepts values of its intended type  
**And** select choices match the options supplied in the configuration  
**And** labels, help text, and validation errors are displayed in Spanish for both countries.

### AC-US01-08 — Unavailable or invalid configuration

**Given** the app is retrieving the country configuration  
**While** retrieval is in progress  
**Then** a loading state is displayed and progression is prevented.

**Given** retrieval fails or the configuration is invalid or has no published form fields  
**When** the user opens step 1 or retries  
**Then** a clear recoverable error state is shown with a retry option  
**And** the user cannot progress  
**And** previously entered quote data is preserved during a recoverable failure  
**And** stale configuration is not presented as current  
**And** no other country's configuration is used as fallback  
**And** user-facing configuration errors do not expose internal technical details.

Invalid configuration includes unsupported field types, duplicate field identifiers, unsupported or incompatible validation operators, missing mandatory properties, required selects with no valid options, and no published fields. When valid configuration becomes available, values are reconciled under AC-US01-14 and the form is revalidated.

### AC-US01-09 — Published field configuration changes take effect

**Given** fields are added, removed, or reordered, or their labels, help, validations, options, or types change in the published Strapi configuration for the current country  
**When** the user reloads the application or switches the URL to that country  
**Then** the refreshed field set and order match the published configuration  
**And** no frontend code change or redeployment is required.

### AC-US01-10 — Keyboard, accessible labels, and responsive form

**Given** the user opens the form on a mobile or desktop viewport  
**When** the user completes and validates the form using only the keyboard  
**Then** every field has an accessible label and can be reached and operated by keyboard  
**And** the form remains usable at both viewport sizes.

### AC-US01-11 — Country context missing from URL

**Given** the application URL does not identify a country  
**When** the user opens the application  
**Then** a country selection screen is displayed.

### AC-US01-12 — Stable field identifiers

**Given** each dynamic field has a unique stable identifier independent of its display label and order  
**When** a field's label or order changes in the published configuration  
**Then** the field retains its identifier.

### AC-US01-13 — Country URL behavior and data isolation

**Given** the user opens a supported lowercase country path segment `co` or `cl`  
**When** the application loads country content  
**Then** the URL remains the source of truth for the active country  
**And** quote data for one country is not used as quote data for the other country.

**Given** the path segment is an uppercase equivalent, if uppercase values are supported by the architecture  
**When** the application accepts it  
**Then** it is normalized to the canonical lowercase code.

**Given** the path segment is unsupported  
**When** the application loads  
**Then** it displays a clear error and allows selection of a supported country  
**And** it does not silently default or redirect.

### AC-US01-14 — Reconcile values when configuration changes

**Given** previously entered values are associated with stable field identifiers and a refreshed valid configuration becomes available  
**When** the form reconciles its values  
**Then** values for removed fields and changed identifiers are discarded  
**And** values for reordered fields and fields with updated labels or help are preserved  
**And** new fields initialize empty or with their configured default  
**And** after validation-rule changes, only compatible values are preserved and revalidated  
**And** after field-type changes, values are preserved only if compatible with the new type  
**And** selections for removed options and all removed or incompatible values are cleared from active persisted state and quote summary  
**And** the whole form is revalidated and progression is blocked while invalid.

### AC-US01-15 — Typed values and validation rule evaluation

**Given** fields use the specified value formats and configured validation rules compatible with their field types  
**When** the form is validated  
**Then** text values are strings, number values are numbers, select values are stable option identifiers, date values use ISO `YYYY-MM-DD`, and checkbox values are booleans  
**And** identity-document numbers and vehicle license plates are treated as strings  
**And** all configured rules are evaluated with one displayed error per field in the precedence defined by AC-US01-02.

### AC-US01-16 — Required select with options and without options

**Given** a required select has one or more valid options  
**When** the field is initially displayed  
**Then** it has a non-selectable placeholder and no option is auto-selected  
**And** it remains invalid until the user selects a valid option  
**And** the required error appears on blur or an attempt to continue.

**Given** a required select has zero valid options  
**When** the country configuration is validated  
**Then** the configuration is invalid and the form is unavailable under AC-US01-08.

## Proposed commands and project conventions

No runnable app or test commands can be specified from the current repository state because this is a pre-implementation specification. The developer and QA stages should record the actual focused test and build commands after an implementation is available.

Implementation must follow `AGENTS.md`: Angular 21+ standalone components, signals, built-in control flow, and no NgModules; Strapi 5+; typed dynamic form configuration with explicit runtime validation; accessible labels and keyboard operation; responsive mobile and desktop behavior; fictional data only. No Strapi write-privileged token may be exposed to the browser.

## Boundaries

- **Always:** Preserve US-01 traceability; limit fields to the active country; validate configuration at runtime; display configured validation errors; preserve entered values when returning from step 2; follow project accessibility and fictitious-data constraints.
- **Ask first:** Change this approved scope, introduce a new dependency, make consequential country/configuration/persistence decisions not resolved in the approved spec or ADR, or change the selected interpretation of age and vehicle-year boundaries.
- **Never:** Attribute human-provided clarifications to the original assessment; put a Strapi write token in the browser; use real personal or payment data.

## Out of scope / deferred

- US-02 plan listing and plan selection.
- US-03 summary, terms and conditions, and simulated payment.
- Complete quote-flow end-to-end verification, deferred until its dependent stories are implemented.
- Exact CO/CL document and plate patterns, unless approved as part of the configured validation contract.

### Details for the architecture proposal

- Define the validation operator-to-field-type compatibility matrix and parameter formats while supporting every listed operator and value format. Reconcile the assessment's field-level required flag with the `required` operator. Clarify required-checkbox semantics, and how `minimumAge` and `vehicleYearRange` bind to fields.
- Define how configured defaults are represented. This draft reads “empty or configured default” as using a configured default when present and otherwise an empty value. Confirm whether defaults must satisfy the field's type and current validations and how an incompatible default is handled.
- Define compatibility when validation rules or field types change. Preserve compatible values, clear incompatible values from active persisted data, and revalidate the whole form as specified above.
- Define which configuration properties are mandatory and how field and select-option identifiers are represented, while retaining the source-required properties and stable identifier behavior.
- Define the field-value schema details, including numeric precision for vehicle years and parameter formats for date-based rules.
- Decide whether uppercase `CO` and `CL` URL equivalents are accepted and normalized. The owner permits this, but does not require it. If not accepted, the unsupported-code behavior applies.
- The final quote-summary presentation test is deferred until US-03 exists. US-01 verification can confirm discarded values are absent from active persisted quote data and its summary payload.
